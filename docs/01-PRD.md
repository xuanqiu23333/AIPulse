# AIPulse V1 产品需求文档

> 状态：设计草案；日期：2026-10-13。项目根目录规划为 `D:\Projects\AIPulse`。本文件描述目标产品，不能视为现有代码已实现的功能。现有能力与证据见 [02-BASELINE-AUDIT.md](02-BASELINE-AUDIT.md)。

## 1. 产品定位与目标用户

AIPulse 是供**一位个人用户**使用的全球 AI 资讯聚合与深度研究 Agent。它定时收集 GitHub Releases、arXiv、Hacker News 的公开动态，将同一事件合并，给出可追溯的中文摘要和每日简报；用户可选中一条资讯继续进行多轮研究，并在 Web 页面查看进度、证据和报告。

目标用户是需要每天快速了解 AI 模型、工具、论文及行业讨论，同时希望对少数事件追查原始出处的独立开发者或研究者。V1 的成功标准是：每天可稳定产出有来源、可回看的简报；从一条简报资讯可启动、观察并取得带来源的研究报告。

## 2. 使用场景

1. **早间浏览**：用户打开 Web 页面，查看指定日期的 AI 简报，按重要性和类别浏览条目，并点开原始链接。
2. **追踪发布**：用户查看关注的 GitHub 仓库最新 Release，了解版本、发布时刻、主要变化和对应原始发布页。
3. **筛选论文与讨论**：用户浏览 arXiv 新论文和 Hacker News 讨论；一篇论文被 HN 转发时，能够看到合并后的事件及两个来源。
4. **深度研究**：用户从资讯卡片发起研究，观察查询、检索、摘要、反思等步骤，最后阅读带引用和来源清单的中文报告。
5. **失败恢复**：单个来源超时或模型不可用时，页面显示失败范围与可重试动作；已取得的其他来源数据仍可浏览。

## 3. V1 功能需求

| 编号 | 功能 | V1 范围与可观察结果 |
| --- | --- | --- |
| F01 | 来源配置与采集 | 配置关注的 GitHub 仓库、arXiv 查询或分类、HN 列表和 AI 关键词；支持每天自动采集及手动触发。记录来源 ID、原始 URL、标题、摘要或正文摘录、发布时间、抓取时间、来源类型和采集状态。 |
| F02 | 标准化与去重 | 在来源内按稳定 ID 去重；跨来源按规范化 URL、论文 ID、Release 标识及可解释的标题相似规则归并。保留每条原始记录和全部来源链接，不因归并丢失证据。重复执行同一窗口采集不生成重复资讯。 |
| F03 | AI 相关性、分类与评分 | 过滤明显无关内容；将资讯标记为模型/研究论文/开发工具/产品发布/行业讨论等少量可配置类别；输出 0–100 重要性分及简短理由。规则信号与模型判断分开记录，低置信度内容可保留为“待查看”。 |
| F04 | 中文摘要 | 每条入选资讯生成简洁中文摘要，准确区分来源陈述与推断，保留原文标题、日期和可点击来源。摘要失败时显示原始元数据，不伪造摘要。 |
| F05 | 每日简报 | 依据可配置时区和日期窗口生成一份中文简报，展示日期、生成时间、条目数、分类、重要性、短摘要、来源与采集覆盖情况；可在 Web 页面回看历史简报。当天再次生成可更新同一日期版本，不重复堆积。 |
| F06 | 多轮深度研究 | 从一条资讯及其来源启动有边界的 LangGraph 研究：拟定问题、检索、证据整理、反思缺口、必要时追加检索、形成报告。明确最大轮数、超时及失败状态；保留每轮查询、引用 URL、时间和状态。 |
| F07 | Web 界面与过程展示 | 单用户本地 Web 页面提供简报列表、资讯详情、研究启动、运行进度/节点事件、报告查看。页面清楚区分“正在运行、完成、部分完成、失败”。 |
| F08 | 报告与来源 | 报告包含主题、结论、支持依据、未证实或矛盾点、生成时间、来源清单；关键事实可回到可点击的原始 URL。无法取得充分证据时明确说明，不将搜索摘要当成已核验事实。 |
| F09 | 本地持久化与重跑 | 保存原始资讯、归并关系、评分摘要、简报及研究运行记录，以支持重启后回看和失败重试。V1 以单机、单用户为部署边界。 |

### 建议的最小数据边界

采集记录（`source_type + source_id + canonical_url + published_at + fetched_at + raw_excerpt`）与归并后的资讯事件分开保存；简报引用事件版本；研究运行引用选中事件和证据快照。这样可保留来源、支持重跑，并防止研究时外部内容变化导致报告无法追溯。具体表结构留待实施计划确定。

## 4. 非功能需求

- **可追溯性**：每条摘要、评分和报告均可定位原始记录及 URL；保留生成时间、模型配置和采集状态。来源不可达时标注，而不悄悄替换。
- **可靠性**：单个来源失败不阻断其他来源；网络请求有超时、有限重试与退避；自动任务具备幂等性。研究任务的停止条件必须可验证。
- **性能与成本**：适配个人电脑或单台轻量服务器；先筛选和去重，再调用 LLM；限制每天采集条数、正文长度、研究轮数及并发。具体预算按选定模型和部署环境测量后确定。
- **安全与隐私**：API 密钥仅在服务端环境变量中使用，不进入网页、日志或报告；外部 URL 抓取限制协议、目标地址、跳转及响应体大小；外部内容作为不可信数据处理，避免提示注入影响指令与引用。
- **可维护性**：采集器和研究工作流通过清晰的数据模型衔接；优先使用简单本地存储与单进程任务机制，避免为个人使用引入分布式队列、微服务或复杂权限体系。
- **兼容性与可用性**：中文界面与报告，保留英文原题；支持常见桌面浏览器；时间统一以 UTC 存储并按用户配置时区呈现。

## 5. V1 明确不做

- 多用户注册、团队协作、租户隔离、细粒度角色权限、商业订阅和支付。
- 全网无边界爬取、社交平台私有数据采集、绕过网站限制或抓取付费正文。
- 对每条资讯自动开展深度研究；研究仅由用户选中后启动。
- 新闻事实真实性的自动最终裁决、投资建议或未经来源支持的预测。
- 大规模向量数据库、分布式任务队列、Kubernetes、复杂微服务拆分。
- 邮件、即时通讯推送、移动端原生应用和公开发布平台（可作为后续版本讨论）。

## 6. V1 验收标准

| 编号 | 可复现的验收方式 |
| --- | --- |
| A01 | 使用固定测试数据分别模拟 GitHub Release、arXiv 论文和 HN 资讯，手动采集后均生成含稳定来源标识、URL、发布时间和抓取时间的记录；来源失败时有独立错误状态。 |
| A02 | 同一采集窗口连续运行两次，事件总数不增长；同一论文的 arXiv URL 与 HN 转发归为一个事件，两个原始来源仍可打开；不同事件不因相似标题被误合并。 |
| A03 | 每条入选资讯展示类别、0–100 评分、评分理由与中文摘要；低置信度或模型失败有显式标记，不能显示虚构事实。 |
| A04 | 指定日期和时区生成简报，页面可按日期回看；简报条目可跳转原始来源及资讯详情；当某来源失败时显示覆盖缺口。 |
| A05 | 从任一资讯启动研究后，页面能按顺序显示每轮查询、检索、摘要/反思、完成或失败事件；达到配置上限后终止。 |
| A06 | 完成的报告含可点击来源、证据与结论；使用缺失来源、空搜索结果和互相矛盾的测试数据时，报告明确表示证据不足或冲突。 |
| A07 | 模拟一个来源超时、LLM 返回非结构化文本和中途重启，其他来源数据可用，失败研究可诊断并重试，不产生重复简报或重复运行记录。 |
| A08 | Web 页面或导出内容不含 API 密钥；对本机地址、私有网段及异常跳转的外部抓取请求按约定策略拒绝；超长响应不会无界进入模型上下文。 |

## 7. 待确认决策

1. 默认运行方式：仅个人电脑按需启动，还是在单台服务器上常驻定时运行；这决定每日任务调度与失败补跑方式。
2. 模型策略：沿用 Ollama/LMStudio 本地模型，还是允许可选云模型；需结合中文摘要质量、机器资源和费用确定。
3. 默认采集范围：GitHub 仓库白名单、arXiv 分类/查询、HN `newstories` 或 `topstories` 的选择，以及每天条目上限。
4. 简报的默认时区、生成时刻与回溯窗口；用户目前位于 `Asia/Shanghai`，但尚未明确这是产品默认值。
5. 重要性评分的权重和分类表；V1 应先以可解释规则和人工样例校准，再决定模型参与程度。
